# 🎯 `GOALS.md`

> **DevHub — سند اهداف و چشم‌انداز پروژه**
> این سند توضیح می‌دهد **چرا** این پروژه وجود دارد، **برای چه کسی** ساخته شده، و **چه چیزی** باعث موفقیتش می‌شود.

---

## 🌟 ۱. چشم‌انداز (Vision)

> **«DevHub جایی است که کیفیت پروژه‌های متن‌باز، توسط خودِ جامعه سنجیده می‌شود — نه فقط با یک ستاره.»**

ما باور داریم که پروژه‌های خوب باید **دیده بشن**، **نقد بشن**، و **به کار گرفته بشن** — بدون اینکه توسعه‌دهنده مجبور باشه برای جلب توجه، بازی الگوریتم‌ها رو یاد بگیره.

---

## 🎯 ۲. مأموریت (Mission)

ساخت یک پلتفرم فارسی که سه کار را **بهترین شکل** انجام دهد:

| #   | مأموریت                   | چرا مهم است؟                                      |
| --- | ------------------------- | ------------------------------------------------- |
| ۱   | **کشف پروژه‌های باکیفیت**  | GitHub فقط محبوبیت را نشان می‌دهد، نه کیفیت        |
| ۲   | **جمع‌آوری بازخورد واقعی** | سازنده‌ها نیاز دارند بدانند پروژه‌شان چقدر مفید است |
| ۳   | **نمایش حرفه‌ای پروژه**    | گالری، دمو، دانلود، مستندات — همه در یک صفحه      |

## 🔥 ۳. مشکل‌هایی که حل می‌کنیم

### مشکل ۱ — «پروژه‌های خوب گم می‌شوند»

**وضعیت فعلی:**
- یه پروژه‌ی عالی توی GitHub هست، ولی فقط ۵ ستاره داره
- یه پروژه‌ی مشابه با تبلیغات ۵۰۰۰ ستاره داره
- توسعه‌دهنده نمی‌تونه بفهمه کدوم واقعاً بهتره

**راه‌حل DevHub:**
- امتیاز از کاربرانی که **واقعاً استفاده کرده‌اند**
- رضایت درصدی (نه فقط بله/خیر)
- نقد مفصل با عنوان + متن

### مشکل ۲ — «بازخورد سازنده‌ها کم است»

**وضعیت فعلی:**
- سازنده پروژه رو می‌ذاره، فقط ستاره و issue می‌بینه
- نمی‌فهمه کاربرا **چی رو دوست داشتن**، **چی رو نه**
- بازخورد صریح و دقیق وجود نداره

**راه‌حل DevHub:**
- Review با امتیاز (۰-۵) + رضایت (۰-۱۰۰) + عنوان + متن
- کامنت‌های تو در تو برای بحث
- Like روی نظرات مفید

### مشکل ۳ — «نمایش پروژه‌ها یکنواخت است»

**وضعیت فعلی:**
- یه README خالی، یا یه متن بلند بدون ساختار
- دموی پروژه کجاست؟
- فایل دانلودی کجاست؟
- اسکرین‌شات‌ها کجان؟

**راه‌حل DevHub:**
- گالری تا ۱۰ تصویر + ویدیو دمو + فایل ZIP
- شرح Markdown + HTML (sanitize شده)
- تمام اطلاعات در یک صفحه، بدون پرش بین سایت‌ها

### مشکل ۴ — «کشف بر اساس محبوبیت، نه کیفیت»

**وضعیت فعلی:**
- GitHub Trending بر اساس ستاره‌های اخیر
- Product Hunt بر اساس upvote
- هر دو **قابل دستکاری** (botted)

**راه‌حل DevHub:**
- **Hot Score** با decay زمانی (Hacker News style)
- پارامترها: stars, forks, downloads, rating, reviewCount, images, video, file
- **تازگی مهم‌تر از تجمع** (پروژه‌ی جدید شانس دیده شدن داره)

## 👥 ۴. مخاطبان هدف (Personas)

### 👨‍💻 Persona 1 — «توسعه‌دهنده‌ی کاوشگر» (کاربر عادی)

```
نام: علی، ۲۸ ساله، برنامه‌نویس Full-Stack
سناریو: قبل از شروع یه پروژه‌ی جدید، می‌خواد ببینه کسی قبلاً این کار رو کرده؟
نیاز: مقایسه‌ی سریع پروژه‌های مشابه + دیدن نظرات واقعی
رفتار: جستجو → فیلتر → خواندن ریویو → کلیک روی GitHub
```

**چی از DevHub می‌خواد:**
- جستجوی سریع و دقیق
- امتیاز و نظرات قابل اعتماد
- لینک مستقیم به دموی زنده + کد

### 🚀 Persona 2 — «سازنده‌ی پروژه» (کاربر عادی → admin)

```
نام: سارا، ۳۲ ساله، توسعه‌دهنده‌ی مستقل
سناریو: پروژه‌ش رو نوشته، می‌خواد بازخورد بگیره و دیده بشه
نیاز: نمایش حرفه‌ای + بازخورد دقیق + آمار
رفتار: ساخت پروژه → آپلود media → تگ → منتشر → بررسی آمار
```

**چی از DevHub می‌خواد:**
- صفحه‌ی نمایش حرفه‌ای
- Analytics (بازدید، دانلود، امتیاز)
- بازخورد صریح از کاربران واقعی

### 👑 Persona 3 — «مدیر جامعه» (admin)

```
نام: رضا، ۳۵ ساله، مدیر محتوا
سناریو: باید مطمئن بشه که محتوای نامناسب و spam فیلتر می‌شن
نیاز: تایید کتگوری‌ها، مدیریت کاربران، نظارت بر کیفیت
رفتار: صف pending → approve/reject → پاسخ به گزارش
```

**چی از DevHub می‌خواد:**
- صف کارآمد برای تایید
- ابزارهای مدیریت کاربران
- قدرت مداخله سریع

### ⚡ Persona 4 — «دولوپر پلتفرم» (developer)

```
نام: محمد، ۲۶ ساله، DevOps
سناریو: مسئول uptime، performance، و امنیت بک‌اند
نیاز: مانیتورینگ real-time + لاگ‌ها + ردیابی خطا
رفتار: بررسی system dashboard → چک لاگ‌ها → دیباگ
```

**چی از DevHub می‌خواد:**
- Dashboard فنی با health checks
- لاگ‌های زنده و قابل جستجو
- هشدارهای خودکار

## 💎 ۵. ارزش‌های محصول (Product Values)

### ۱. **کیفیت بر کمیت**
- یه ریویوِ صادقانه ارزشمندتر از ۱۰۰ upvote الکیه
- الگوریتم‌ها طوری طراحی شدن که پروژه‌های خوب کوچیک هم دیده بشن

### ۲. **شفافیت**
- هر کاربر می‌تونه ببینه **کی**، **کِی**، و **چرا** یه نقش داده
- هیچ feature پنهانی وجود نداره

### ۳. **جامعه‌محور**
- کاربران عادی هم می‌تونن تگ اضافه کنن
- کتگوری‌های جدید از درخواست کاربران می‌آن
- هیچ تصمیمی بدون شفافیت گرفته نمی‌شه

### ۴. **تکنیکال اما ساده**
- پیچیدگی فنی توی بک‌اند (الگوریتم Hot Score، JWT، OTP)
- تجربه‌ی ساده توی فرانت (بدون تنظیمات پیچیده)
- فارسی RTL از روز اول

### ۵. **امنیت پیش‌فرض**
- OTP اجباری قبل از هر عمل حساس
- Session revocation روی تغییر رمز
- بدون compromise بین امنیت و UX

## 🎨 ۷. اصول طراحی (Design Principles)

### 🎯 اصل ۱ — «بدون آموزش قابل استفاده است»

- کاربر باید بدون تور راهنما، بتونه پروژه بسازه
- هر عمل باید بازخورد فوری داشته باشه (toast, shake, dialog)
- خطاها با پیام فارسی واضح، نه کد ۴۰۰

### 🎯 اصل ۲ — «همه چیز قابل بازگشت است»

- حذف پروژه → confirm dialog با هشدار
- تغییر ایمیل → rollback اگه لغو شد
- کامنت با reply → soft delete
- تغییر نقش → audit trail

### 🎯 اصل ۳ — «موبایل اول در استفاده، دسکتاپ اول در توسعه»

- کاربر ۷۰٪ از موبایل استفاده می‌کنه → تجربه‌ی موبایل بی‌نقص
- توسعه‌دهنده با دسکتاپ کار می‌کنه → داشبورد غنی

### 🎯 اصل ۴ — «تاریکی، نه به‌عنوان trend، به‌عنوان راحتی»

- تم تیره برای چشم‌های خسته از کد
- رنگ‌های تأکیدی کم (فقط برای CTA و status)
- کنتراست مناسب برای خوانایی طولانی

### 🎯 اصل ۵ — «فارسی، نه ترجمه»

- تمام UI فارسی اصیل، نه ترجمه‌ی ماشینی
- RTL از روز اول، نه بعد از
- اعداد فارسی در نمایش، لاتین در کد

## 🎯 ۱۰. چرا این پروژه **حالا**؟

### زمان‌بندی درست است چون:

1. **موج متن‌باز در ایران**: تعداد پروژه‌های متن‌باز فارسی در ۲ سال اخیر ۳ برابر شده
2. **GitHub هنوز «کیفیت» را نشان نمی‌دهد**: ۲۰۲۴ و همچنان فقط ستاره!
3. **Stack Overflow کاهش فعالیت**: فرصت برای جایگزین فارسی
4. **ابزارهای SSR دوباره محبوب شدند**: EJS + Express ساده و سریع
5. **MongoDB + TypeScript mature**: دیگه نمی‌شه گفت «برای MVP فقط»

### ریسک‌های اصلی

| ریسک                       | احتمال  | کاهش ریسک                      |
| -------------------------- | :-----: | ------------------------------ |
| **cold start** (کاربر اول) | 🔴 بالا  | Seed محتوا + دعوت از community |
| **spam / fake reviews**    | 🟡 متوسط | Rate limit + admin approval    |
| **کمبود محتوا**            | 🟡 متوسط | Import از GitHub Trending      |
| **رقابت با GitHub**        | 🟢 پایین | DevHub = مکمل، نه رقیب         |
| **مشکل حقوقی**             | 🟢 پایین | فقط لینک، نه copy کد           |

### ✅ از دید ادمین:

## 💭 ۱۲. فلسفه‌ی نهایی

> **DevHub نمی‌خواد «GitHub بعدی» باشه.**
>
> می‌خواد جایی باشه که وقتی **«کدوم پروژه رو استفاده کنم؟»** می‌پرسی، جواب دقیق‌تری از ستاره‌ها بگیری.
>
> وقتی **«پروژه‌م چطوره؟»** می‌پرسی، بازخورد واقعی بگیری.
>
> وقتی **«چی جدید هست؟»** می‌پرسی، چیزهایی ببینی که واقعاً **بهترین** هستن، نه **پرصداترین**.
